# Audit — 2026-09-10

A slow read of the whole repository at `8fc3a8f`: every module in `Sources/`, the test
target, the benchmark package, the experiments, CI, and the front-door documents. Six
questions were asked of it — code quality, organisation, tests, benchmarks, dead code,
developer experience — and each finding below names its evidence so it can be checked
rather than trusted.

**Method.** Files were read in full or outlined and sampled; three probes were compiled
and run against the actual macro to confirm what the type checker does and does not
catch; a declaration-reference sweep was scripted over `Sources/`, `Tests/` and
`Benchmarks/`; and a clean build was done with warnings counted. Nothing here is a
guess about behaviour — where a claim is "silently accepted", a struct was written,
expanded and executed to see it be silently accepted.

**Verdict, in one paragraph.** The engineering underneath is unusually good: no
`fatalError`, no `TODO`, six force-unwraps all on `baseAddress!`, every `@unchecked`
justified in a comment, zero `print` or `try!` leaks in tests, every design decision
recorded with its date and the measurement that made it. The problems are almost all at
the *surface* — the part a developer meets in the first hour — and they are the kind
that a project this careful about internals produces precisely because the internals
absorbed the care. The four that matter most: **`print(error)` on the library whose
headline is error reporting prints `AssayError(storage: Assay.AssayError.Storage)`**;
**`@Schema(discriminator: .none)`, the documented spelling, emits a compiler warning on
every use**; **eleven attribute combinations are accepted at expansion and silently do
nothing**, against a principle the project states in three places; and **the library
builds with 56 warnings**, which means the next real one will not be seen.

## 1. Developer experience

This is listed first because it is where the gap between "how good the code is" and
"how good it feels to use" is widest, and the user asked for the highest quality
experience.

### 1.1 `AssayError` and `Issue` are not printable — **HIGH**

`Sources/Assay/Entry.swift:76`, `Sources/AssayCore/Issue.swift:91`.

Compiled and run:

```
do { _ = try P3S.parse(json: #"{"a":"x","name":""}"#) } catch { print(error) }
// AssayError(storage: Assay.AssayError.Storage)

error.localizedDescription
// The operation couldn’t be completed. (Assay.AssayError error 1.)

print(d.issues[0])
// Issue(code: AssayCore.IssueCode.typeMismatch, path: [AssayCore.PathComponent.key("a")],
//   params: ["expected": AssayCore.IssueValue.string("integer")], received: Optional("\"x\""),
//   location: Optional(AssayCore.SourceSpan(lo: 5, len: 1)))
```

`AssayError.render(.plain)` produces the beautiful caret output the README leads with —
but nothing calls it for you. Every place a Swift developer *sees* an error without
asking — `print`, string interpolation, a `#expect(throws:)` failure, `XCTAssertNoThrow`,
a crash log, Vapor's default error middleware, `localizedDescription` in an alert — shows
the line above. A first-time user's first failing decode looks like a library that does
not report errors.

`Diagnosis` is worse: its synthesized description dumps `SourceBytes` as an array of
integers.

**Fix.** `AssayError: CustomStringConvertible` returning `render(.plain)`;
`Issue: CustomStringConvertible` returning `"\(path): \(message)"`; `Diagnosis:
CustomStringConvertible` rendering issues or "valid". `LocalizedError` (`errorDescription`)
belongs in `AssayFoundation`, since the core is Foundation-free — but it should exist,
because `localizedDescription` is what every Apple-platform error surface reads. Half a
day, and it changes the first impression more than any other item in this document.

### 1.2 `discriminator: .none` warns on every use — **HIGH**

`Sources/Assay/Assay.swift:219` declares `discriminator: Discriminator? = nil`;
`Assay.swift:490` declares `Discriminator.none`. The parameter is Optional, so `.none`
resolves to `Optional<Discriminator>.none`:

```
UnionTests.swift:331:25: warning: assuming you mean 'Optional<Discriminator>.none';
    did you mean 'Discriminator.none' instead?
```

Twenty-four of those in this repository's own test build. The macro reads the token and
works anyway, which is how it shipped — but the spelling `EXPERIENCE.md` §9 documents
produces a warning in every file that uses it, and the note suggests a spelling
(`Discriminator.none`) that makes the attribute read worse.

**Fix.** Rename the case. `.untagged` says what it means, cannot collide with
`Optional.none`, and reads better in the attribute: `@Schema(discriminator: .untagged)`.
One day old, no users; rename it now. Alternatively make the parameter non-optional with
a third case `.absent` as the default — but a case a user is never meant to write is
worse than an Optional the macro already handles.

### 1.3 Attribute combinations that are accepted and do nothing — **HIGH**

`CLAUDE.md`, `UnionGen.swift` and `docs/UNIONS.md` all state the principle: *an option
that is accepted and then does nothing is worse than one that is refused.* Today's union
work found and fixed four instances on unions. A probe of the struct path — every case
below was expanded with no diagnostic, then **compiled and executed** — found eleven more:

| declaration | what happens | should |
|---|---|---|
| `@Schema @XML(root: "book") struct S` with no `.xml` format | root never checked, never written | diagnose: `@XML(root:)` needs `formats: .xml` |
| `@XML(.attribute) var a` with no `.xml` format | placement ignored | same |
| `var a: Int; @Extras var rest: [String: RawValue]` with default `unknownKeys: .ignore` | `rest` is always empty | diagnose, or imply `.collect` — the sink is the declaration of intent |
| `@Schema(unknownKeys: .reject)` + `@Extras` | keys rejected, sink never filled | diagnose: contradictory |
| `@Key("x") @Key(path: "a.b") var a` | `@Key("x")` silently ignored; `"x"` does not decode | diagnose — and the doc-comment on `Key(path:)` (`Assay.swift`) says this *cannot* be combined; it can |
| `@Ignore @Validate(.min(1)) var a` | rule never runs | diagnose |
| `@OneOrMany var a: Int` | ignored | diagnose: needs an array |
| `@Fallback(1) var a: Int?` | accepted | probably fine, but say so in the doc — "a fallback on an optional" has a non-obvious meaning |
| `@Coerce var a: String` | `1` → `"1"` | the `@Coerce` doc says `var host: String // 8080 stays an error`; with the attribute it does not — document or refuse |
| `@Preprocess(.trim) var a: Int` | type-checker error **inside the expansion**: `cannot convert value of type 'Int' to expected argument type 'String'` at `macro expansion @Schema:71` | diagnose at expansion the way `@DateFormat` and `@Validate` already do |
| `@Schema struct S {}` | expansion is empty, no diagnostic; `S.parse` does not exist | diagnose (`SchemaMacro.swift:254` is `guard … else { return [] }`) |

`@DateFormat` on a non-`Date` *is* refused with a purpose-written message, and
`@Validate(.min)` on the wrong type *is* refused — so the machinery exists and the
pattern is established. This is the same audit that found `formats: .all` on a union
this morning; the class is systematic and the fix is one table of checks in
`SchemaMacro.expansion`, each a diagnostic naming the alternative.

### 1.4 The public surface is the macro runtime — **MEDIUM**

`Sources/Assay/Assay.swift:12` is `@_exported import AssayCore`. `AssayCore` has
**~150 public functions** whose only caller is generated code: `decodeInt16OrNull`,
`keyWindow(_:byteOffset:shift:)`, `enterContainer`, `chargeUnionAttempt`,
`scanDiscriminator`, forty-five `decode*` variants in `Decode.swift` alone. Every one
of them appears in a user's autocomplete on `reader.` and in the module's documentation.

The generated code needs them public; nothing says they need to be *discoverable*.
Options, cheapest first: (a) an `@_spi(Generated)` group so they exist for the
expansion and vanish from the documented surface; (b) a `_` prefix, which the codebase
already uses for `_assay`, `_assayEncode`, `_assayBatch` and which DocC hides by
convention; (c) an `AssayRuntime` namespace enum with the primitives as statics taking
`inout AssayReader`. (a) is the right one — it is exactly what SPI groups exist for and
costs one line per declaration.

### 1.5 `IssueCode` is mostly strings — **MEDIUM**

`Sources/AssayCore/Issue.swift:68`: ten enum cases and `.custom(String)`. Across
`Sources/` there are **27 distinct `.custom("…")` codes** (`union_unknown_variant`,
`yaml_empty_stream`, `xml_root_mismatch`, `unsupported_media_type`, every validation
code…), and the documented advice is "match on `code`, never on `message`". Four of them
have a named static (`.fallbackApplied`, `.unrepresentableValue`, `.extrasKeyCollision`,
`.unknownNotEncodable`); twenty-three do not, so a user writes
`issue.code == .custom("union_unknown_variant")` from memory and gets no autocomplete,
no typo protection and no place to read what params the code carries.

**Fix.** A named static per code, declared where the code is raised (each format module
can extend `IssueCode`), with a doc-comment listing its `params`. The enum design is
right — a closed enum cannot cross the module boundary — the statics are the missing
half. Then the `codeString` table in `Messages.swift` and the renderers' JSON output
have one source of truth.

### 1.6 `Rule` API is inconsistent — **LOW**

`Sources/AssayCore/Rule.swift:184–241`. `.email`, `.url`, `.uuid`, `.hostname`, `.ascii`
and `.notEmpty` each come in two spellings, a static and an `(or message:)` function.
`.trimmed`, `.lowercased`, `.positive`, `.negative`, `.nonNegative`, `.finite`, `.unique`
have only the static — no way to attach a message. And `.trimmed`/`.lowercased` are
*assertions* (the value must already be trimmed), which `CLAUDE.md` records as a thing a
test had to catch; the names read as normalisations, and `@Preprocess(.trim)` is the
normalisation. `.isTrimmed`/`.isLowercase` would make the test unnecessary.

### 1.7 Front door staleness — **LOW**

- `README.md:23`: "`ROADMAP.md` lists what is deliberately deferred, **encoding
  included**" — encoding shipped 2026-08-09.
- `README.md:55`: `.package(url: "https://github.com/<owner>/assay.git"` — the remote is
  `nerdmenot-swift/assay`.
- `Package.swift:11`: "AssaySIMD is a separate target so the BuiltinModule feature is
  contained to it" — phase 4 was retired 2026-08-08 and the target does not exist.
- `Sources/AssayCore/MediaType.swift:100`: "`lowercased()` on a `String` is
  locale-sensitive" — it is not; Swift's `String.lowercased()` is locale-independent.
  Foundation's `lowercased(with:)` is the locale-sensitive one. The code is right (ASCII
  folding is still the correct choice for a Foundation-free core); the stated reason is
  wrong.

## 2. Code quality

### 2.1 The library builds with 56 warnings — **HIGH**

A clean build (`touch Sources/*/*.swift && swift build`), unique by location:

| count | warning |
|---|---|
| 41 | expression uses unsafe constructs but is not marked with 'unsafe' `[#StrictMemorySafety]` |
| 8 | no unsafe operations occur within 'unsafe' expression |
| 5 | public import of 'X' was not used in public declarations or inlinable code |
| 1 | enum 'Storage' has storage involving unsafe types (`SourceBytes.swift`) |
| 1 | deprecated default implementation … `MemberMacro` conformance should implement the `expansion` function that takes a `conformingTo` parameter (`WrapsGen.swift:118`) |

`Package.swift:72` enables `.strictMemorySafety()` on every non-macro target. That is
the right setting for a library whose hot path is raw pointers — and then 41 sites do
not honour it and 8 sites over-mark. The setting is therefore decorative: the next
genuinely unmarked unsafe expression is invisible in the noise. The test build adds ~180
more, the largest group being 102 × "trailing closure in this context is confusable with
the body of the statement" from `#expect { … }` and `withUnsafe… { … }` in tests.

**Fix.** Zero the library warnings (an afternoon: the 41 are mechanical `unsafe`
insertions in `MappedFile.swift`, `AssayReader.swift`, `Render.swift`,
`JSONValueDecode.swift`, `MappedParsing.swift`; the 8 over-marks are deletions; the 5
imports become plain `import`), then add `-warnings-as-errors` to CI for `Sources/`
only. The generated-code warnings (`variable '__sp3' was never mutated`, `'as' test is
always true`) are the macro's to fix — emit `let` where the slot is never reassigned.

### 2.2 `SchemaMacro.expansion` is 356 lines — **MEDIUM**

`Sources/AssayMacros/SchemaMacro.swift:143–499`. One function parses eight options,
walks members, flattens `@Inline`, validates six things, builds the dispatch plan, emits
eleven optional bodies and assembles a conformance list. It works, and the comments are
good, but it has the shape that grows a bug per feature: today's `formats: .all` slip
lived in exactly this kind of function on the union side.

The same file repeats this four times (encode, xml, sources, describes):

```swift
for message in Self.encodeDiagnostics(activeS) { context.diagnose(…) }
guard Self.encodeDiagnostics(activeS).isEmpty else { return [] }
```

— computing the diagnostics twice each. A `func refuse(_ messages: [String]) -> Bool`
removes eight lines and the double evaluation.

**Fix.** Split into `SchemaConfig.parse(node)` (options → one struct),
`SchemaAnalysis` (members → fields, groups, checks, with every refusal in one table —
which is also where §1.3's missing refusals go), and `SchemaEmitter` (bodies →
conformances). The gate measures generated-body size, not macro-source structure, so
this is free at compile time.

### 2.3 Deliberate repetition, worth a generator — **LOW**

`Sources/AssayCore/Decode.swift` is 641 lines of 15 scalar types × 3 variants
(`decodeX`, `decodeXOrNull`, `decodeXCoercing`), each a 7-line function differing in
one type name and one string. Hard constraint 6 requires the monomorphic entry points,
so the repetition is right; but the file is now hand-maintained across 45 near-identical
bodies, and the last width addition touched all three families. A `gyb`-style template
(or a shell generator like `gen_types.sh`, checked in beside its output) would make the
next scalar a one-line change and make drift between the three families impossible.

`String(unsafeUninitializedCapacity:)` one-copy construction appears three times
(`Strings.swift:68`, `Collectible.swift:79`, `AssayReader.swift:512`); one
`@inlinable` helper would do.

### 2.4 Generated code quality — **LOW**

The expansion is readable, well-commented, and the naming (`__f0`, `__ck0`, `__sp3`) is
consistent. Two things a user stepping through it in a debugger will notice: the emitted
`var __extras`/`var __spN` slots that the compiler warns are never mutated (see §2.1),
and that the tagged-union arms are indented one level deeper than the `switch` that
contains them (`UnionGen.swift`, `taggedEncodeBody`/`taggedBody`). Cosmetic, but
expansions are what users read when something goes wrong.

cost a moment every time someone opens the wrong one. `Rules.swift` and
`IssueCollector.swift` would not.

## 4. Tests

**Count and shape.** 630 tests, 105 suites, all `swift-testing`, 0.13 s wall. No `print`
leaks, no `.value!`, fifteen `try!` (all in fixtures, acceptable), one temp-dir use with
cleanup. The macro is tested directly through `expandSchemaForTesting` in
`MacroTests.swift`, which is what made today's refusal tests possible — that helper is a
genuine asset. Assertions prefer `code ==` (117) over `message` string matching (43),
which is the right ratio. The suites that carry the design's weight — `UnionErrors`,
`RewindTests`, `AmplificationTests`, the differential oracles in `DiffFuzz` — are
exactly the ones a reviewer would ask for.

### 4.1 Untested public surface — **MEDIUM**

A symbol-to-test-file sweep found these with **zero** test references:

| symbol | note |
|---|---|
| `KeyNamingStyle.kebabCase`, `.pascalCase`, `.screamingSnakeCase` | three of the five key styles. `KeyStyle.split` handles acronyms and digits with hand-written rules (`WindowSearch.swift:135`) and only `.snakeCase` exercises them |
| `Issue.message(locale:)` | the localisation seam, documented in `EXPERIENCE.md`; no test passes any locale |
| `diagnose(mmapped:)` | `parse(mmapped:)` has one test file; the diagnose form none |
| `WireFormat`, `MediaType.parse` directly | reached only through `parse(body:)`; the RFC 6839 suffix rules (`+json`, quoted charset, `us-ascii`) have no unit test of their own |
| `render(.terminal)` | one reference; the colour/no-TTY branch is not pinned |
| `Rule.trimmed`, `.lowercased`, `.positive`, `.negative`, `.nonNegative`, `.finite`, `.unique`, `.ascii`, `.prefix`, `.suffix`, `.contains`, `.oneOf`, `.multipleOf` | some are exercised by `ValidateBench`'s differential, none by name in `Tests/` |

### 4.2 No golden expansion test — **MEDIUM**

`MacroTests.swift` checks expansion *shape* (`contains("_assayEncode")`, the window
table is sparse) but no test pins a whole expansion for a representative type. That is
how `__assayCaseNames` (§6) was emitted into every `@Unknown` enum with no reader for
however long it has existed, and how `CLAUDE.md`'s "context-free expansion is
byte-identical (verified by dumping one)" was verified once by hand rather than on every
run. One golden file per generator (decode, raw, encode, union, wraps, describe) with a
diff on failure would catch every accidental change to emitted code — which, under the
compile-time budget, is the change class that matters most.

### 4.3 Test organisation — **LOW**

`UnionTests.swift` (666 lines) now holds four concerns — tagged decode, tagged failure
reporting, untagged, encoding — and will keep growing; `ColumnarSourceTests.swift`
(623) and `PlistTests.swift` (577) are in the same position. Fixture types are declared
at file scope with a prefix per file (`Union…`, `Enc…`, `Untagged…`), which works but
means a reader of one suite scrolls past the fixtures of three others. A `Fixtures/`
subdirectory, or one file per suite, would keep each under ~300 lines.

## 5. Benchmarks

**What is good.** `RESULTS.md` is honest to a degree that is rare: every arm states what
it did not measure, every ratio names its machine, the allocation gate turns itself off
when its self-check fails, predictions were written before runs and kept when wrong. The
oracles in `DiffFuzz` found real parser bugs on their first run. The compile-time gate
is min-of-3 with the reasoning for every statistic written beside it.

### 5.1 One monolithic run with no arm selection — **HIGH** (for the developer, not the numbers)

`Benchmarks/Sources/AssayBench/main.swift:456–486` runs twenty arms sequentially with no
way to select one; `CommandLine` is never read. A full run is ~8 minutes, and every
benchmark-affecting change today cost that, twice, while a concurrent compile-time
measurement contaminated the second run and had to be discarded. The allocation gate's
exit code arrives only after all twenty arms.

**Fix.** `AssayBench [arm…]` with the arm names that already exist as `run*` functions,
`AssayBench --list`, and the allocation gate as its own arm so CI can run it alone.
Half a day; it repays itself the first afternoon anyone benchmarks anything.

### 5.2 `RESULTS.md` is a journal, not a table — **MEDIUM**

1446 lines in chronological sections (`# Phase 1`, `# The full corpus`, `# YAML and
XML`, `# Dates`, …, `# Making the XML parser faster`). A reader asking "what is the
current struct-decode ratio on macOS?" has to know that the 5.44× on line 30 was
superseded by 8.98× in a later section, then 9.17× in the sweep. The journal is
valuable — keep it — but it needs a **current-numbers table at the top**, regenerated
by the harness, with each row linking to the section that produced it. `CLAUDE.md`'s
status table is currently doing this job by hand and drifts (macOS struct decode is 9.17×
on line 21 and 8.98× on line 38, two runs of one arm).

### 5.3 Benchmark package hygiene — **LOW**

- `Benchmarks/Package.resolved` is git-ignored. The results quote Yams, ZippyJSON and
  swift-syntax versions implicitly; a reproducer six months from now resolves different
  ones. Track it for the benchmark package specifically (the library's stays ignored).
- `pad` and `measure` are defined in `main.swift` and used by every arm file; `DiffFuzz`
  has its own `pad`. A `BenchSupport.swift` in each executable would remove the
  top-level-script coupling that currently forces `AllocFailures` to be a class box.
- `ColdStartTypes.swift` (1762 lines) is generated by `gen-coldstart.py`; the file says so
  in a header but nothing in CI regenerates and diffs it, so the generator and its output
  can drift the way `Corpus/` is explicitly protected against ("Corpus determinism" job).

## 7. What to do first

In order of leverage per hour, with the estimate being one person's:

1. **`CustomStringConvertible` on `AssayError`, `Issue`, `Diagnosis`; `LocalizedError` in
   `AssayFoundation`** (§1.1). Half a day. Changes what every new user sees first.
2. **Rename `Discriminator.none` → `.untagged`** (§1.2). One hour, while there are no
   users to break.
3. **Zero the 56 library warnings and add `-warnings-as-errors` to CI for `Sources/`**
   (§2.1). One afternoon. Makes `strictMemorySafety` mean something.
4. **The refusal table** (§1.3): eleven expansion-time diagnostics for accepted-and-ignored
   combinations, in one place, each with a test through `expandSchemaForTesting`. One
   day. This also starts the `SchemaMacro.expansion` decomposition (§2.2) in the right
   direction.
5. **`AssayBench` arm selection** (§5.1). Half a day. Then the current-numbers table at
   the top of `RESULTS.md` (§5.2), generated by the harness.
6. **Named statics for every `IssueCode.custom`** (§1.5) and the `Rule` `(or:)` gaps
   (§1.6). One day together.
7. **Golden expansion tests** (§4.2) and the untested key styles / `message(locale:)` /
   `MediaType` (§4.1). One day.
8. **Hide the macro runtime behind `@_spi(Generated)`** (§1.4). Half a day, but it is an
   API-shape decision worth making before 0.1.0 and awkward after.
9. Dead code (§6), file splits (§3), doc staleness (§1.7). An afternoon, any time.

Items 1–4 are what stands between this codebase and the first-hour experience its
internals deserve.
